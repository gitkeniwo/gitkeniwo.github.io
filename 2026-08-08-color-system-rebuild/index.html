配色系统重做：从手调十六进制到能算出来的色阶

[ 中文 ] [ English ]
ケニヲ
2026-08-08
Zen and the Art of Computer Maintenance › Programming Languages
design , css , color , notes

这个站有两套主题：浅色是粉，深色是终端绿。这篇记录把它们从「一堆手调的十六进制」改成「一条可以算出来的色阶」的全过程 —— 起因、量到的数字、否掉的方案，以及最后落地的结构。

所有色卡、梯子、对比度表都在 /design/colors/ 上，那一页是构建时用 OKLCH 现算的，「今天」那一列直接解析 variables.css。这篇里的数字是论证用的引用，那一页才是权威 —— 我特意没有把表格抄到这里，抄一次就会有第一次对不上的那天。

一、起因：不是页面的问题

最早的抱怨很具体：/irc/ 频道页看起来「凌乱、不像对齐」。

但排查下去，问题不在那个页面的布局，而在变量层 —— 频道页只是把配色的毛病放大到了最容易看见的地方。于是先修配色系统，再谈排版。

二、量到的四件事

所有判断都建立在测量上，而不是「看着不太对」。背景是浅 #e2e0de、深 #1d1f21；cr 指 WCAG 对比度（1 = 看不见，21 = 纯黑配纯白，正文需要 ≥ 4.5）。

1. 浅色主题整体欠对比。 link 3.28、strong 2.06、em 2.73、toc-active 2.39 —— 几乎全线低于 AA 的 4.5，而深色一侧稳定在 7 附近。两个主题不是风格不同，是一个能读一个不能读。

2. 三个几乎一样的粉在打架。 #d44375（23 处）、#c04059（11 处）、#c73866（3 处）：明度差 0.04、饱和差 0.02、色相差 10°。近到眼睛认为「应该是同一个色」，又不够近到真的是。这种「差一点」比明显不同更乱 —— 这就是频道页凌乱的直接原因。

3.「安静层」发棕不是错觉。 深色里当次要色用的 #8dba8a 不是「安静版的绿」：它色相偏黄 21°，而且只用了该明度下三分之一的饱和度。橄榄绿配终端绿，当然不协调。

4. 今天的亮粉没用满色域。 #d44375 在它的明度上只用了 76% 的可用饱和度。推到边缘可以同时更艳、更清楚。也就是说：不需要用酒红换可读性。

三、锁色相梯子

第四点是后面所有方案的地基：锁死色相、保住饱和度、只动明暗。

用降饱和度做「安静层」已经被否决了 —— 试看之后很明确，低饱和的粉和绿读作棕色和卡其，而且离主色跳跃太大、中间没有过渡。而在锁色相的梯子上，每一站都还是粉／还是绿，中间没有断层。

注意一件后面反复要用到的事：「后退」的方向在两个主题里是相反的。深底上变暗 = 对比降低 = 后退；浅底上变暗 = 对比升高 = 加重。这是背景决定的，躲不掉。

四、第二声部：四个候选，一条规则

第一轮只动一个角色 —— 「第二声部」（banner status、[#chan]、日期分隔、tab 星号），主色不动，好把变量隔离出来。四个候选都取自梯子：

候选位移 ΔL方向cr 倍数判定
F 浅 #c51963−0.06远离背景×1.32✓ 选中
E 深 #2ad69c+0.07远离背景×1.29✓ 选中
E 浅 #fb6e9a+0.12朝向背景×0.63褪进背景
D 深 #17825d−0.17朝向背景×0.51褪进背景
D 浅 #a81454−0.12远离背景×1.68方向对，跳跃太大
G 中性灰—退出家族—没有 jump，也没有色彩联系

（主色：浅 #d44375 cr 3.28 · 深 #2bbc8a cr 6.82）

选中的两个不是「各挑各的好看」，而是同一条规则的两次执行：第二声部 = 主色沿梯子朝远离背景的方向走一档。 步长几乎相等（×1.32 vs ×1.29）。要守恒的是每个主题内部的关系，不是跨主题的数值 —— 浅色主题不是深色主题的反相。

被否的两个是同一个错误。E 浅变亮、D 深变暗，看起来完全相反，但在「相对背景」这个真正起作用的坐标里是同一个动作：都朝背景方向走，都走了约两档，都褪掉。

D 浅的酒红方向是对的，问题在步长 —— 一步跨了两档，中间没有过渡，所以显得突兀。它没有被丢掉，见下一节。

五、三档不够，需要一条 ramp

定下 F 浅之后暴露出一个矛盾：解一下「这个色相上第一个过 AA 4.5 的粉是哪个」，答案就是 F 浅本身。也就是说第二声部比主角更清楚 —— 「主色不动」这个前提守不住了。

解法是不再按「主次」分配角色，改按字号：大字的 AA 门槛是 3.0，正文是 4.5。

于是「一眼扫过去是亮粉」靠面积最大的标题和 ASCII 保住，可读性靠正文那一档保住，两者不再抢同一个 token。酒红落在 hover 那一档，中间隔着正文档，跳跃问题自己就没了。

每一档由目标对比度反解出来，不手调十六进制，而且两个主题的目标值故意不相等：深色一侧最响的那档对比度高于正文档，浅色一侧反过来。这不是失误 —— 浅底上最响的粉离背景最近，深底上最亮的绿离背景最远。「响」在两种背景上的代价不同。

顺带一提，浅色那个最响的粉是 #e21e73。标准色名里最近的是 Razzmatazz（#e3256b，Crayola 1993），OKLab 距离 0.015，基本看不出差别；再往下是 Rosa Mexicano #e4007c 和 Ruby #e0115f，中文传统色里最近的是品红。它的色度 0.228 比今天的 #d44375（0.184）更满 —— 更艳且更清楚。

六、角色重排

语义层不出现任何数字，只引用档位：

--color-link:       var(--a-base);   /* 正文级 → AA 那一档 */
--color-link-hover: var(--a-deep);
--color-accent-1:   var(--a-vivid);  /* 标题、ASCII → 最响那一档 */
--color-meta:       var(--n-quiet);  /* 今天是不分主题的死 #666 */

因为语义名不变，全站 289 处 var(--color-*) 大部分一行都不用改。真正的成本是浅色主题每个页面重新过一眼。

顺带修掉的三个历史遗留：

  • --color-meta 与 --color-border 是不分主题的死 #666（浅底 4.36、深底 2.88）—— 这是 IRC 前缀区的灰色在两个主题下表现相反的原因。
  • --color-quote 两个主题饱和度差 6 倍。
  • glow token 在深色用的是青色 rgba(0,255,255,…)，跟全站的绿根本不同族，是历史遗留。

完整的 token 对照表在 /design/colors/，红色标的是低于 4.5 的正文级 token —— 今天浅色那一列基本是一片红。

七、色卡是骗人的

同一个颜色在 12px 的 meta 小字和在一整块 ASCII 图上完全是两回事。所以最后一步是把候选放回真实界面：IRC 频道、首页、正文 markdown，每个都用真实组件和真实数据渲染，现状与提案上下对照。

上下堆叠而不是左右并排，是因为两栏各占一半宽度时，IRC 前缀列和 ls tags/ 网格会在真实站点里根本不会遇到的宽度上换行 —— 对照就从「比颜色」变成了「比 reflow」。

八、这套东西怎么加主题

整套东西只有两个数据源，都是纯函数、无依赖：

文件装什么
scripts/oklch.mjsOKLCH ↔ sRGB、色域上限、WCAG 对比度、solveAgainst(目标对比度, 色相, 背景)
scripts/theme.mjsTHEMES（主题 = 背景 + 色相 + 一组目标对比度）、ROLES（token → 档位）

加一个主题就是往 THEMES 里加一条，只写背景、色相和目标对比度，不写十六进制。梯子、档位、色卡、对照表和所有试色面板都会自动多出一份。

solveAgainst 按背景亮度决定搜索方向，而不是按主题名 —— 所以两个背景不同的深色主题会解出不同的色阶，而不是共用一条。

终端里 node scripts/palette.mjs rungs 打印的是同一份数据。

整件事的方法论其实只有一句：先量，再改。 「看着不太对」是个真实的信号，但它不告诉你哪里不对 —— 「三个粉的明度差 0.04」才告诉你。
